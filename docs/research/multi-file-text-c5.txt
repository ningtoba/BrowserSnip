txt / markdown / html multi-file: the live pair, before and after
=================================================================

Lane `convert`, chunk c5, carry-over 1 (decided in c4, applied here). Dev server :5296
(this worktree), Chromium CDP 9846, `docs/research/colour-rail.mjs` in SPEC mode.

Fixtures (`/tmp/lane-convert/c5x/fx`), two files per route, each holding one marker:

  one.txt / two.txt   `FIRST TEXT FILE …  MKENDONE` / `SECOND TEXT FILE … MKENDTWO`
  one.md  / two.md    `# ONEFILE HEAD` + `Body of the first document, MKENDONE` / "
  one.html/two.html   `<h1>ONEFILE HEAD</h1><p>… MKENDONE</p>` / …

Each run opens the tool, uploads BOTH files through the card's own file input, writes no
fields, clicks the card's own verb, presses the result card's Download, and hands the bytes
back; `pymupdf` then reads the text of every sheet. Screenshots are the same runs.

BEFORE (master 2028d3f, `out-pair-before`, `runs-pair-before.jsonl`)
--------------------------------------------------------------------
Uploading the pair left the second document out of the job entirely: the run reported one
source and the bytes hold only the first file's words.

  txt-to-pdf      Typeset 1 text source(s) into 1 page(s).      143 B → 1.7 KB
      sheet 1: 'FIRST TEXT FILE / Alpha bravo charlie / … / the first file, MKENDONE.'
      MKENDONE True | MKENDTWO False          (one.txt only; two.txt never arrived)
  markdown-to-pdf Rendered 1 Markdown source(s) into 1 page(s). 59 B → 1.3 KB
      sheet 1: 'First Markdown / Body of the first document. / MKENDONE / 1 / '
  html-to-pdf     Laid out 1 HTML source(s) into 1 page(s).     85 B → 1.1 KB
      sheet 1: 'First HTML / Body of the first / page. MKENDONE / '

What the single-document contract says, measured three ways on the same build:
  * the intake line (`out-foot-before`, read off the page with the tool open):
      `Accepts .txt, .log, .md, .markdown · one file at a time · …`
      `Accepts .md, .markdown, .txt · one file at a time · …`
      `Accepts .html, .xhtml · one file at a time · …`
    while the `files` field directly below it says
    `Several files are laid out in the order you added them, one after another in a single PDF.`
  * `ToolSurface.acceptFiles` (`shared/ToolSurface.tsx:190-208`) keeps `[first]` for a tool
    without `multiFile` and prints
    `This tool works on one file at a time, so it is using "one.txt".`
  * the gate itself, when the pair reaches the runner directly (the vitest path):
    `ToolInputError: This tool works on one file at a time. It will use "one.txt".`
    — that is the sentence the new pins catch.

CONTROLS (`out-pair2`, `runs-pair2.jsonl`)
------------------------------------------
  * order: html given `two.html` then `one.html` → `two_from_html.pdf`, sheet 1 =
    'Second HTML / Body of the second page. MKENDTWO', sheet 2 = the first document. The
    order is the order added, and the name is the first file's, not the alphabet's.
  * batch integrity: markdown given one real `.md` plus a PNG named `bad.md` → the run is
    refused with `"bad.md" is a PNG image, not a Markdown file.` and the repair pointer
    `Use Images to PDF, or Digitize Document if the page has text to recognise.` — loud, the
    file named, no stack text (`sourceBatches` throws on the first file the reader rejects,
    the behaviour every text route already had for csv/json/xml/rtf).
  * a form feed inside one file of a batch still breaks that file (`THIRD-A` lands on sheet 3
    of a 2-file/3-sheet run; pinned in `convert-to-bytes.test.ts`).
